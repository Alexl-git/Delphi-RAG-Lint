What can you point at, and what can you ask it?

drag-lint is not a model. It needs a closed set of questions, each one a formal call with a selection and parameters. This is that set — and an honest status for each, because roughly a third of it is not buildable today.

The branching problem — do not take the longest

You asked whether, when a method trace forks, we choose the longest path. I would not. Longest is a proxy for “interesting” and it is a bad one: a deep logging helper or a validation chain will out-run the real path every time.

Follow the payload, not the calls

The question is about a value. So the trace is a data slice, not a call tree: keep a branch only while it still carries the thing you selected. That prunes most forks before ranking ever matters, and it is the reason the OPERAT.NAME trace stayed at 33 steps instead of hundreds.

A trace is defined by its endpoints, not its depth

Declare a closed set of sinks and discard any path reaching none of them:

  • UI — a DFM control, a grid column, a displayed property
  • Database — a SQL table or column
  • Process boundary — pipe, socket, HTTP, serial
  • File or log
  • Dead end — value consumed and discarded. Worth reporting as such; it is often the answer someone wanted.

Rank the survivors, cap the display, and say what you hid

Order by: crosses a process boundary → reaches the database → reaches the UI → terminates internally. Show the top few in full, then collapse the rest as an explicit row — + 17 other branches (not shown) — that expands on click.

Never drop a branch silently. This is the linter rule in a different costume: a finding you hide teaches the reader to distrust every finding you show. A trace that quietly omits the branch someone was looking for is worse than one that admits it capped at five, because the first is indistinguishable from the value genuinely not going there.

When the payload cannot be followed

Say so, in the artifact, at the step where it stopped. Mark each edge [certain] or [inferred] and let the renderer draw inferred edges dashed. A trace with three honest dashed edges is useful; a trace that presents a guess as a fact is the thing this product exists to replace.

The formal call

The IDE should not hard-code the question list. It asks the engine what can be asked about the thing under the caret, renders that as a menu, and sends back an id.

drag-lint ask --list --at <file>:<line>:<col> --db <db> --json
  -> resolves the selection, returns ONLY the questions valid for its kind

drag-lint ask --question protocol-trace \
              --at Blueprint4.ViewModel.pas:1850:24 \
              --db <db> [--depth 6] [--max-branches 5] [--sinks ui,db,boundary] \
              --format dlgraph|script|svg|mermaid|json

Half of this already exists. drag-lint typeat <file>:<line>:<col> already resolves a caret position to a symbol. The selection half of “point at something and choose a question” is solved — ask reuses that resolver and dispatches on the resolved kind.

The shape of that table is the finding. Fourteen questions ship on facts that already exist — days of serializer work, not weeks. Five are assembly. Three have nowhere to read from. Four are blocked, and three of those four are blocked on one defect: protocol command enum values are indexed but never bound to their declaring symbol, so nothing joins a sender in one executable to its handler in another. Sent to the engine team as docs\INBOX-URGENT-engine-facts-for-diagram-questions.md, with the measurement in docs\INBOX-enum-value-refs-never-bound.md.

These artifacts are not autodocumentation. They are large, slow to produce and stable over time, so nothing generates them on a build. Someone asks a question deliberately, and inserts a reference into the code or its documentation. That means the volatility belongs in the FILE — a stable path plus a regenerated artifact — and never in the comment, which also keeps the autodoc rewriter entirely out of it.

What I would do first

  1. Ship a ship now question end to end — who-calls or butterfly. The verb already emits dot. It proves script → unit rectangles → clickable rows → SVG with nothing blocked, and it is days.
  2. Run the one spike that settles three unknowns at once: does a single dot run emit -Tsvg and -Tplain together, does HREF on an HTML-like table cell survive into the SVG, and can Skia hit-test by point.
  3. Then decide on the enum binding. It unblocks three questions including the one you actually want, but it moves DRAGLINT_RESOLVER_VERSION and re-resolves every database — which the workstream plan promised would not happen. That promise needs correcting either way.
