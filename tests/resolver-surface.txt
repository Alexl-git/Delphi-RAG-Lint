#     <repo-relative path>::<RoutineName>      a single top-level routine

# WHY BY FUNCTION AND NOT BY DIRECTORY. The resolve pass straddles two trees:
# src\index\DRagLint.Index.CallResolver.pas and the writers in
# src\storage\DRagLint.Storage.SQLite.pas. No line through the directory tree

#

# ---------------------------------------------------------------------------
# PURITY V2 (2026-09-21). The `purity` resolve stage DERIVES
# symbol_facts.effect_free / effect_summary / effect_witness from rows and
# source the index already holds -- call_edges, member_accesses, refs and the
# routine bodies. A change to the model or to the stage changes what is
# WRITTEN, which is this manifest's own test for surface, and the remedy is
# `index --all --resolve-only`, never a re-parse.
#
# IT IS LISTED EVEN THOUGH THE HEADER ABOVE SCOPES THE SURFACE TO "call_edges,
# type_ancestors, type_helpers and unit_uses". A literal reading of that
# sentence would exclude a stage that writes symbol_facts instead. What decides
# it is the staleness mechanics: TPurityStage recomputes only when
# PurityNeedsRun is True -- i.e. some row with body_loc > 0 still has
# effect_free IS NULL -- so a database already FILLED by an older stage keeps
# its old verdicts FOREVER. There is no other trigger. A resolver-fingerprint
# mismatch is the only thing that forces recomputation, so without these
# entries any future change to purity logic would go silently stale in every
# index, which is precisely the failure mode the baseline's header warns about.
src/analysis/DRagLint.Analysis.Purity.pas::*
src/analysis/DRagLint.Analysis.PurityStage.pas::*
