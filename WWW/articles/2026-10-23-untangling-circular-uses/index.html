Untangling Circular Uses in Delphi

drag-lint finds circular uses groups, names the unit that holds a group together, and removes the cycle for you behind a compile gate that rolls back on failure. This article starts with what is new since it first appeared, then walks one small project from the first report to a project with no cycle left, one command at a time, and ends with how the engine does it and what it refuses to do.

Delphi 13 Florence · RAD Studio 37.0 First published 2026-10-23 · Updated 2026-11-17 for drag-lint 1.51.2-alpha As of 2026-11-17, drag-lint 1.51.2-alpha

The first time this fixer was pointed at real code, it was not a demo: it was a copy of the client project of Micronite, the quality and production-control software we build for manufacturers. drag-lint is the Delphi index and linter we build alongside it, and everything below runs on your own machine.

Automatic, deterministic, no AI. The fix is a Delphi algorithm inside drag-lint. It plans every edit from the index of your project, writes it, and keeps it only after your own RAD Studio compiler has built the project before and after the change. Nobody edits a file by hand, no language model or internet service is asked anything, and the same input gives the same result, byte for byte (section 07 shows the check).

01 — What is new

Since the first version of this article

The first version described two kinds of cut: Part A, which moves declarations into a new leaf unit, and Part B, which cuts one edge of an implementation-only group by one of a few recipes. Both are still there. What changed is the shape that used to defeat them: a hub, one unit that every other unit of the group reaches back into, usually a main form read through its global variable.

  • cycles --hub (since 1.50.0-alpha) names the hub of each group: the unit whose removal leaves the rest of the group free of cycles, the edges and references on each side of it, and exactly what the other units take from it. It only reads the index.
  • Recipe R3, “hub surface”: put the members the other units read through the hub’s global behind an interface in a new unit, let the hub class implement it, and rewrite only the receiver in the other units. AppMainForm.Note(...) becomes AppMainHub.Note(...); the rest of the line stays as it was.
  • cycles --plan picks R3 by default since 1.51 for a group it predicts R3 can break. --no-hub-surface asks for the older planner.
  • cycles --fix --hub-surface (new in 1.51.1) writes R3 through the same compile gate as every other fix: baseline build, backups, build after the edit, rollback on a new error, re-index, and a check against its own prediction. In 1.51.2 you ask for it by name; --fix without the switch still runs the older planner, and so do the IDE’s fix menus.
  • uses-recover is a separate verb for units that ship without source. It reads the vendor’s C++Builder .hpp headers (never a .dcu) to recover their interface uses, so the uses graph does not stop at the edge of a compiled library. It does not fix cycles; it makes the graph the cycle report reads more complete.

The engine’s own documentation records why R3 was built: on a copy of a 78-unit application of ours, with one main form whose global the other 76 units read at 1665 places, the older planner could neither move the form class nor finish the other way round. R3 rewrote 77 files and added one unit; the project built with 0 errors and a re-indexed cycles reported no circular dependency. That run predates the compile gate for R3 and is not repeated here; the small project below is.

02 — The problem

A cycle that compiles is still a cycle

Delphi only forbids a mutual interface-section cycle: if two units use each other in their interface sections, the compiler stops with F2047 Circular unit reference. A cycle closed by an implementation uses compiles fine, and quietly keeps the units welded together: a change to one recompiles the others, and none of them can be tested or reused alone.

The running example is a console program, Shop.dpr, with four units. AppMain declares the class TAppMain and the global AppMainForm; its Run procedure calls TakeOrders, CheckStock and PrintReport, so its implementation uses Orders, Stock and Reports. Each of those three uses AppMain back, to reach the global. One of them:

unit Orders;

interface

procedure TakeOrders;

implementation

uses
  System.SysUtils, AppMain;

procedure TakeOrders;
begin
  Inc(AppMainForm.OrderCount, 3);
  AppMainForm.Note('orders taken: ' + IntToStr(AppMainForm.OrderCount));
end;

end.

The shape of many older VCL programs: a main form with a global, and units that reach back into it through that global. Small enough to read in full, real enough to need every step below.

03 — Step by step: find it

Where to see the cycles

Cycle detection reads the unit-to-unit uses edges from the drag-lint index, not from the files on disk, so the project must be indexed first.

In the IDE

Menu path

drag-lint > Uses & Dependencies > Circular Uses Report (cycles + fix plan)...

The menu item runs cycles --plan --edges --causes against the active project’s index and writes the result as a text report; since 1.51 that report holds the R3 plan for a hub-shaped group (step 3). Two other entry points show the same cycles from a different angle:

  • drag-lint > Reports > Circular unit dependencies... draws a chart of each group with every measured uses edge inside it and how heavy each edge is.
  • The drag-lint Structure window’s Diagnostics tree carries a circular-uses warning on every unit that is part of a cycle. The rule is on by default.

On the command line

Every command below runs in the project folder. The index is in _D-RAG\Shop.sqlite, the standard place for a project’s index. The commands carry --library-db none, which tells drag-lint not to read a platform library index; this demo uses only two RTL units and needs none. The index is built once:

drag-lint index --project Shop.dproj --db _D-RAG\Shop.sqlite --library-db none
...
Done. Files: 5, Symbols: 19, Refs: 63, 0.18s, parse-errors=0

Step 1. List the circular groups, then the edges inside them.

drag-lint cycles --db _D-RAG\Shop.sqlite --format text --library-db none

1 circular unit group(s) found:
  [4 units] reports <-> stock <-> orders <-> appmain   (implementation-only -- legal, lower impact)
  (add --edges for the uses lines, --causes for the symbols to refactor)
drag-lint cycles --edges --db _D-RAG\Shop.sqlite --format text --library-db none

1 circular unit group(s) found:
  [4 units] reports <-> stock <-> orders <-> appmain   (implementation-only -- legal, lower impact)
      reports uses appmain  [implementation]
      stock uses appmain  [implementation]
      orders uses appmain  [implementation]
      appmain uses orders  [implementation]
      appmain uses stock  [implementation]
      appmain uses reports  [implementation]

Six edges, all in implementation uses clauses, so the compiler accepts the group. A group with an interface edge would be flagged “has interface coupling -- widest recompile blast radius” and listed first. Six edges also means six places to cut, and most single cuts do nothing because the circle goes round another way.

Step 2. Ask for the hub. A hub is a unit whose removal leaves the rest of its group free of cycles: cut every edge on one side of it and the circle is gone.

drag-lint cycles --hub --db _D-RAG\Shop.sqlite --format text --library-db none

1 circular unit group(s) found:
  [4 units] reports <-> stock <-> orders <-> appmain   (implementation-only -- legal, lower impact)
      hub appmain: in 3 edges (3 impl, 0 intf) 14 refs, the in-side alone breaks the group: yes; out 3 edges (3 impl, 0 intf) 3 refs, the out-side alone: yes
        spoke->hub surface: 1 symbols -- var AppMainForm 7 refs in 3 units (4 member names: Note 4, OrderCount 3, Log 1, Ready 1)
        hub->spoke surface: 0 constructions, 0 var writes, 0 var reads, 0 method calls in 3 units
        lighter side: spoke->hub (1 hub symbols vs 3 spoke surfaces)
      zero-ref edges inside the group: 0 of 6

AppMain is the hub. Three edges come in, three go out, and either side alone breaks the group. The surface line is the important one: the three other units (the spokes) use exactly one symbol of the hub, the global AppMainForm, and through it only four members: Note, OrderCount, Log and Ready. That is the shape R3 handles: put those four members behind an interface in a new unit, and let the spokes use that unit instead of the hub. The last line says every edge carries at least one real reference; an edge with zero would be a uses entry that can simply be deleted.

The plan says what will change before anything does: a new unit AppMain.Hub with the interface IAppMainHub and a global AppMainHub of that type; TAppMain implements the interface and sets the global when it is created; the seven uses of AppMainForm. in the spokes become AppMainHub.; and the three spokes drop AppMain from their uses clause. The last item is a prediction: no cycle left among these four units. The apply in step 6 checks it.

The “write it” line names cycles --plan --hub-surface --apply, which writes without building. Use the gated cycles --fix --hub-surface of steps 5 and 6 instead.

05 — Step by step: fix it

A dry run, then the same command with --apply

Step 5. The dry run. It plans the fix, stages the result in a temporary shadow tree, and builds the project as it is now, the baseline build. A project that does not build before the edit is refused (section 06). No source file is written. The baseline build writes what any build writes: DCUs and the exe.

...

“Verdict: mechanical” means every step of the plan can be done by rule, with nothing left for a person to decide. The progress lines go to stderr, so stdout keeps only the result. Each step prints a line when it starts and, while it runs longer than 10 seconds, one more every 10 seconds. On a quiet machine this dry run printed only cycles --fix: baseline build -- started; in a second capture, on a machine busy with other builds, the same baseline took 15 s and printed (path shortened):

cycles --fix: baseline build -- started
cycles --fix: baseline build -- 10 s (no time limit; Cancel, or drag-lint shutdown --db "...\shop\_D-RAG\Shop.sqlite", stops it)

There is no time limit unless you set one with --build-timeout <s>. drag-lint shutdown --db <db>, or Cancel on the IDE’s status strip, asks the engine to stand down: it kills the build and, on an apply, rolls back. (The first version of this article showed that cancel on 1.42.0-alpha; it was not repeated for this update.)

Three details show that this is a rewrite by rule, not a search and replace. Inc(AppMainForm.OrderCount, 3) became an assignment, because OrderCount is now an interface property and Inc does not accept a property. The fields Log and OrderCount got a getter and a setter each; the methods Note and Ready are in the interface as they are. And the global is set in AfterConstruction before inherited, so code that runs in a form’s OnCreate already sees it. TComponent does not reference-count its interfaces, so holding the object in an interface variable does not change its lifetime. The hub keeps its own global: Run still creates and frees the object through AppMainForm.

The build after the edit is the check that matters. As a further check, beyond the gate, we ran the program before and after the fix; both print the same three lines:

orders taken: 3
stock checked
report: 3 orders

drag-lint cycles --db _D-RAG\Shop.sqlite --format text --library-db none

No circular unit dependencies found.

The --apply run already did this check itself (“Verified: the re-indexed `cycles` output matches the prediction”). AppMain still uses the three spokes; they no longer use it.

The same fix from the IDE

There are three places to start a fix in RAD Studio. All three run cycles --fix with the active project, its index and the IDE’s active platform. In 1.51.2 they do not pass --hub-surface, so they run the older planner shown in step 3; R3 through the gate is a command-line step for now.

Where What you click What it does
The drag-lint menu drag-lint > Uses & Dependencies > Fix Circular Uses Mechanically (dry run)... Dry run only

The engine picks the group. There is no apply from a menu click. Save all files first: the engine plans and compiles from disk.
The Uses & Deps tab View > Tool Windows > drag-lint, tab Uses & Deps, section This project -- Circular uses (cycles --fix) Dry run, then Apply

One row per cycle group, with Dry run and Apply buttons. Apply asks first (Yes / No, default No).
The Structure window Diagnostics tree, right-click a circular-uses finding: Fix this cycle (dry run)... or Apply cycle fix... Dry run, confirm, apply

Apply cycle fix... runs the dry run, asks you, and only then runs the apply.

What you accept or refuse. The apply confirmation is built from the dry run’s result: the units of the cycle, the recipe and the edge it cuts, how many files will be edited, the names of any new units, the baseline build status and time, and what happens if the build fails. The default button is No; answering No leaves the files untouched. The IDE refuses to apply while any file the plan edits has unsaved changes, and a refused verdict has no Apply at all. What you accept with Yes is bounded: every file is backed up as <file>.BCK<n> with a recovery.txt, the project is built in place, and if that build fails, or you press Cancel, every file is put back. (These IDE steps are as described in the first version of this article and in the engine’s documentation; the screens were not re-captured for 1.51.1.)

06 — Step by step: when it says no

Three runs that changed nothing, and why

A fix that writes source is only as good as its refusals. Each run below starts from a fresh copy of the Shop project with one line changed, and runs the full --apply command of step 6. After each one, every .pas file was byte-identical to what it was before the run.

The recipe cannot reach every use. Stock.pas reads the global through a with block:

  with AppMainForm do
    if Ready then
      Note('stock checked');

R3 rewrites only the receiver in front of a dot, and inside a with there is none. That spoke would still use AppMain, so the group would stay. drag-lint says so and writes nothing:

- spokes: 2 rewritten (5 receivers `AppMainForm.` -> `AppMainHub.`), 1 refused
  - refused `Stock.pas`: with-member -- line 14: `with AppMainForm do`: a with block needs restructuring
...
- prediction: the group stays -- 1 spoke->hub edges remain
...
Verdict: refused
  - hub-surface-group-stays:  :0 -- the group stays -- 1 spoke->hub edges remain (the planner's own fix: drop --hub-surface)
compile: baseline 1.1 s

Exit code 1. A partial fix that leaves the circle in place is not offered as a fix.

The project does not build to begin with. One line in Reports.pas calls a routine that does not exist. The baseline build fails, and the run stops before it plans an edit:

Verdict: refused
  - dirty-baseline:  Shop.dproj:0 -- the project does not build before any edit (2 dcc error line(s), first: Reports.pas(14): error E2003: Undeclared identifier: 'NoSuchRoutine' [...\shop-dirty\Shop.dproj]); fix it, then retry
    Reports.pas(14): error E2003: Undeclared identifier: 'NoSuchRoutine' [...\shop-dirty\Shop.dproj]
    AppMain.pas(27): error F2063: Could not compile used unit 'Reports.pas' [...\shop-dirty\Shop.dproj]
compile: baseline 0.8 s

Without a clean baseline, an error after the edit could not be told apart from an error that was already there.

The edit does not compile: the real rollback. Orders.pas passes the field to a routine with a var parameter:

procedure AddThree(var pCount: Integer);
begin
  Inc(pCount, 3);
end;

procedure TakeOrders;
begin
  AddThree(AppMainForm.OrderCount);

A field can be passed as a var parameter; an interface property cannot. In 1.51.2 the recipe does not catch this case itself, so it plans the fix and writes it. The compiler catches it in the build after the edit, and drag-lint puts every file back:

- spokes: 3 rewritten (7 receivers `AppMainForm.` -> `AppMainHub.`), 0 refused
...
Verdict: refused
rolled back, project not changed
  - compile-error:  Shop.dproj:0 -- the project does not build after the edit (2 dcc line(s), first: Orders.pas(19): error E2197: Constant object cannot be passed as var parameter [...\shop-var\Shop.dproj]); rolled back, project not changed
compile: baseline 0.9 s, after 0.8 s

Exit code 1. The capture script checked afterwards: the sources were byte-identical to before the run, and the new unit AppMain.Hub.pas was not left behind. This is what the compile gate is for: the recipe is a set of rules, and rules have gaps; the gate makes sure a gap costs one refused run, not a broken project. The rollback restores the sources, not the DCUs the failed build wrote, so build once more after a rollback.

07 — Step by step: same input, same result

08 — How DL does it inside

Not magic: the index, a graph, and rules

Every answer above comes from facts drag-lint stored when it indexed the project, then from plain graph algorithms and fixed rules over those facts. This section follows the run in that order. It is taken from the engine’s design notes and the doc comments of its source, not from memory.

What the index stores

Fact What is stored What the cycle fixer uses it for
Uses edges Every entry of every uses clause, with the section it sits in (interface or implementation) and its line The graph the groups are found in; which edge is interface coupling; where a uses entry is moved or removed
Symbols Every declaration with its kind (class, field, method, global variable, routine, constant, ...) and its exact lines What can move, what is a plain field and what is a method, where a body starts and ends
References Every use of a name, with its position and the text of its receiver: in AppMainForm.Note(...), the reference Note carries the receiver AppMainForm How heavy an edge is; which members the spokes read through the hub’s global; the exact places to rewrite
Call edges and ancestry Which routine calls which; each class’s ancestors, followed into the platform library index Whether a method body uses the cycle; whether a member comes from your code or from an RTL or VCL ancestor

Finding the groups

The engine builds a directed graph from the uses edges: one node per unit, one arrow per uses entry, with a bare unit name bound to a project unit the way dcc binds it (unit scope names included). A library unit is a node with no arrows out. It then runs Tarjan’s algorithm for strongly connected components: a set of units in which each one can reach every other one by following arrows. Every component of more than one unit is a circular group. That is why the report draws a group, not a ring: two loops that share a unit are one group. The same pass feeds the circular-uses lint finding, so the report and the Structure window cannot disagree. The cycles dcc rejects with F2047 are found the same way, over the interface edges alone.

Finding the hub

For each unit of a group, the engine removes it and tests whether the rest is acyclic. A unit that passes is a hub: every cycle of the group goes through it. For each hub it then tests the two sides separately: cut only the edges coming in, then only the edges going out, and see whether the group still has a cycle. On the Shop project:

            +--> Orders  --+
  AppMain --+--> Stock   --+--> AppMain      every arrow: an implementation uses
            +--> Reports --+

  without AppMain:   Orders    Stock    Reports     no arrow left between them -> acyclic
  cut only the 3 arrows into AppMain   -> no cycle  ("the in-side alone breaks the group: yes")
  cut only the 3 arrows out of AppMain -> no cycle  ("the out-side alone: yes")

The cost is one acyclicity test per unit of the group over the group’s own edges, plus one read of each unit’s symbols and references. It only reads the index; it never runs the planner, opens no library and needs no project file.

The surface of each side

The surface is what actually crosses an edge, counted from the references. For the spoke-to-hub side, the engine lists the hub’s symbols the spokes use, and for a global variable it counts the member names read through it: the references whose receiver text is that global. That is the “var AppMainForm 7 refs in 3 units (4 member names: Note 4, OrderCount 3, Log 1, Ready 1)” line. For the hub-to-spoke side it counts kinds: constructions of spoke classes, writes and reads of spoke variables, and method calls. Per edge, --causes --format json gives the same facts in finer grain: members read, writes, construction, class methods, and routines with the types in their signatures. The “lighter side” line compares the two: hub symbols on one side, distinct spoke surfaces on the other. R3 always cuts the spoke-to-hub side; on Shop that is also the lighter one.

Choosing a recipe

The fix has two parts and four recipes. Which one runs depends on the shape the index shows:

Recipe When it applies What it writes
Part A: leaf move The group has interface coupling. Removes that coupling, leaving at most a legal implementation-only group. Enums, records, constants, variables, and classes whose method bodies use nothing of the cycle, move unchanged into a new leaf unit <Declaring>.Untangle. A class whose bodies use the cycle stays, and a base class carrying only the members the other units read can be extracted into the leaf instead. Each consumer then keeps, moves or removes its uses entry.
Part B, R1: routine-call inversion An edge made of routine calls whose signatures name no class of the cycle. A procedural type and variable in a leaf; the declaring unit assigns the variable in its initialization section; the consumer calls through it.
Part B, R2: member hand-over An edge made of is / as checks against a class plus reads of its members. An I<Class>Surface interface in a leaf that the class implements; the consumer goes through Supports / as on the interface.
R3: hub surface Exactly one hub, read by the spokes through one global instance of a class declared in the hub unit. A new leaf <Hub>.Hub with an interface of the members the spokes read (a property per field, a method per method) and a global of that type; the hub class implements it with accessors and the AfterConstruction / BeforeDestruction hand-over; a receiver-only rewrite in each spoke. A free routine of the hub that a rewritten spoke still calls goes through an R1 pointer in the same new unit.

For Part B, every edge of the group is weighed in a fixed order, and the plan prints it: “move globals, routine-call inversion, member hand-over; within one recipe the edge whose surface has the fewest members, then the fewest references, wins. One edge is cut per run.” Since 1.51, before any of that, --plan asks R3 whether it predicts the group breaks; if yes, the group is planned by R3, and if not, the plan is byte for byte what --no-hub-surface prints. A refusal in R3 is per member and per spoke: one member the interface cannot carry leaves only the spokes that read it untouched, and if that leaves an edge to the hub, the whole group is refused with hub-surface-group-stays.

Every plan ends with a prediction of what cycles will print after the edit (“the group breaks -- no cycle left among these 4 units”, or the exact expected text in the older planner’s checklist). The apply holds itself to it.

The gate

  baseline build     msbuild /p:Config=Debug, the platform you name (the IDE passes its own)
       |             does not build? -> dirty-baseline, nothing written
       v
  shadow tree        the plan staged in C:\TEMP\draglint_cyclefix_<pid>\, checked line by line
       |             a file changed since it was indexed? -> stale-file / anchor-mismatch
       v             (dry run stops here: "Verdict: mechanical")
  write              --apply only: every touched file backed up as <file>.BCK<n> first
       |
       v
  build after        a new error? -> every file put back: compile-error, rolled back
       |
       v
  re-index           the project index is brought up to date
       |
       v
  verify             cycles again; its output must equal the prediction -> "Verified"

The write is all-or-nothing: a write or build that fails part-way ends with every file restored byte for byte, or, if the restore itself fails, the failure named. For the planner’s own recipes one bounded repair is allowed on a compile error (R4, such as a missing leaf unit in a uses clause) before the rollback. An apply that skips the compile is refused outright: --apply --no-compile is exit 2.

0exit: mechanical, or written and verified
1exit: refused, rolled back, or written but not verified
2exit: error (bad flags, a write or build failed part-way)

The same hub report on a real code base

The demo has one obvious hub. Real groups are less tidy. drag-lint 1.51.1-alpha, run on a copy of the index of drag-lint’s own source as it stood on 2026-11-15, finds two groups. In the five-unit group only one unit qualifies as a hub:

drag-lint cycles --hub --db ...\dl.sqlite --format text --library-db none
...

      hub draglint.doc.regions: in 3 edges (3 impl, 0 intf) 28 refs, the in-side alone breaks the group: yes; out 2 edges (1 impl, 1 intf) 157 refs, the out-side alone: yes

09 — What it will not do

The refusals, and why

The engine never guesses. Every refusal prints as Verdict: refused with one line per reason that names the symbol, file or line it stopped at, which is where a hand edit starts. The kinds fall into a few families:

Family Examples Why it stops
The run and the gate dirty-baseline, compile-error, build-timeout, cancelled, no-compiler, stale-file, anchor-mismatch, outside-roots, non-ascii-text (and the exit-2 pair build-error, write-failed) Unsafe to write

None of these judges your code; each names a condition the proof needs: a clean baseline, a build after the edit that passes, files that are what the index saw, edits inside the project’s own roots (shared code the gate cannot prove for other projects), text the target file’s ANSI encoding can carry, a RAD Studio build environment (--rsvars <rsvars.bat> names one).
The plan (Part A / B) base-class, blocked-symbol, directive, unresolved-edge, edge-still-used, coupling-remains, declaration-in-include, reference-in-include, manual-edit A human decision

A class whose method bodies use the cycle cannot move, and a base class stands in for it only at a closed list of use sites. A conditional directive around an edited uses entry, a use the index cannot explain, a cut after which the consumer still needs the other unit, a moved set that cannot share one leaf, a declaration or use inside an {$I} include file (drag-lint never edits an include, which other units may share), or text the planner does not rewrite: each refuses and names its line.
R1, routine-call inversion overloaded-routine, signature-in-cycle, init-order, finalization-order, routine-not-called, name-shadowed, duplicate-identifier Order and binding matter

The pointer is assigned in the declaring unit’s initialization, so a call that could run before it, or after the unit is finalized, refuses. So does a routine named without being called (@Foo), an overload the argument counts do not settle, and a line where another declaration shadows the name.
R2, member hand-over member-write, member-unsupported, construction, class-method, with-member, ref-counted, exception-semantics The interface is not enough

Creating the object needs the class; a class method, a write a setter cannot carry, a with body whose names would bind elsewhere, a reference-counted class (releasing the temporary interface would free it), or a handler that relies on EInvalidCast refuses.
R3, hub surface hub-surface-group-stays, and per spoke with-member and the others below One spoke, not the group

Refused per spoke: a with <global> do block (section 06), a write to the global or to a designer field, a member that is not a plain field or method of the hub class, the global passed as a var parameter, FreeAndNil, CreateForm or @ of the global. Assigned(<global>) and a bare use of the global are rewritten, the latter through an AsForm function typed with the hub class’s one library ancestor. When a refused spoke keeps its edge to the hub, the group refuses as a whole: hub-surface-group-stays.
What stays manual

A refused group is yours. --plan still prints the playbook and the standard remedy for it. Moving a class whose method bodies use the cycle, creating objects through an interface, and any cut a refusal names, stay human decisions.

10 — Limits

Honest edges

  • R3 does not yet handle a field passed as a var parameter. AddThree(AppMainForm.OrderCount) is rewritten to a property, which dcc rejects with E2197; the gate rolls the whole fix back (section 06). The recipe refuses the global itself as a var argument, not a member read through it.
  • R3 through the gate is opt-in in 1.51.2. cycles --fix without --hub-surface, and every IDE fix menu, run the older planner. cycles --plan --hub-surface --apply writes R3 with no compile gate at all: build the project after it, or use --fix --hub-surface.
  • R3 fits one shape: one hub that the other units read through one global. A group with several hubs, or a hub reached through its own routines and constants, gets the older planner or a refusal that names why.
  • The new unit is not added to the project file. AppMain.Hub.pas was not added to Shop.dpr or Shop.dproj; the project builds because the unit sits in the same folder, but the IDE’s project tree does not show it until you add it.
  • It builds your project. A dry run costs one full build; an apply costs two, or three with the one repair. On a 625-file Micronite client project a dry run took about two minutes, measured on an earlier drag-lint build. --no-compile skips the build in a dry run only.
  • One group per run. With no --cycle or --unit, the first mechanical group is planned and the rest are named, not touched.
  • Part A does not always remove the cycle. It removes the interface coupling; what can remain is a legal implementation-only group for Part B. The plan says so before it writes anything.
  • A passing build does not prove the behaviour is unchanged. The gate proves the project compiles. We ran the Shop program before and after; run your own tests, and read the diff of an apply.
  • The answers are only as fresh as the index. Reindex the project first. A unit that ships without source has no uses edges in the index; uses-recover can add its interface uses from the vendor’s .hpp headers.
  • An implementation-only cycle is legal Delphi. The report calls it lower impact; fixing it is a choice, not an obligation.

The whole fix, start to end: cycles finds the group, cycles --hub names the hub, cycles --plan shows every edit before it is made, and cycles --fix --hub-surface --apply makes them, building the project before and after, rolling back on any compile error, and checking its own prediction against a fresh index. It is a Delphi algorithm inside drag-lint: no AI, and the same project gives the same result every time.
