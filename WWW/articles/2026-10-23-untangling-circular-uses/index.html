Untangling Circular Uses in Delphi

drag-lint finds circular uses groups, shows them in the RAD Studio IDE, and can cut one edge for you behind a compile gate that rolls back on failure. This article walks through what you click and what you see first, then what the engine does underneath — and, just as important, what it refuses to do.

Delphi 13 Florence · RAD Studio 37.0 Real output as of 2026-10-29, drag-lint 1.38.0-alpha

We build drag-lint alongside our main product, Micronite — quality and production-control software for manufacturers — and the cycle fixer was tried on copies of that product’s own client project as well as on the small demos below.

01 — The problem

A cycle that compiles is still a cycle

Delphi only forbids a mutual interface-section cycle: if two units use each other in their interface sections, the compiler stops with F2047 Circular unit reference. A cycle that is closed by one implementation uses compiles fine — and quietly keeps the units welded together. Our running example is two units from the drag-lint repository, docs\examples\circular-uses-demo.

unit Customers;
interface
uses
  Orders;              { interface uses: half of the cycle }
type
  TCustomer = class
  private
    FOrders: TArray<TOrder>;   { forces the uses }
  ...

unit Orders;
interface
type
  TOrder = class ... end;   { holds its customer as a TObject }
implementation
uses
  System.SysUtils,
  Customers;           { implementation uses: closes the cycle }

Customers needs TOrder in its interface. TOrder.Describe reads the customer’s name, so Orders reaches back into Customers from its implementation. Legal, but a change to Orders now recompiles Customers and vice versa.

02 — In the IDE: the report

Where to click to see the cycles

Cycle detection reads unit-to-unit uses edges from the drag-lint index, not from the files on disk, so the project must be indexed first. Then, in RAD Studio:

Menu path

drag-lint > Uses & Dependencies > Circular Uses Report (cycles + fix plan)...

The menu item runs cycles --plan --edges --causes against the active project’s index and writes the result as a text report. Two other entry points show the same cycles from a different angle:

  • drag-lint > Reports > Circular unit dependencies... draws a chart of each group with every measured uses edge inside it and how heavy each edge is.
  • The drag-lint Structure window’s Diagnostics tree carries a circular-uses warning on every unit that is part of a cycle. The rule is on by default.

What the report says

For the demo, the edge listing and the cause listing are, verbatim:

1 circular unit group(s) found:
  [2 units] customers <-> orders   (has interface coupling -- widest recompile blast radius)
      customers uses orders  [interface  <-- move-to-implementation candidate]
      orders uses customers  [implementation]

1 circular unit group(s) found:
  [2 units] customers <-> orders   (has interface coupling -- widest recompile blast radius)
      * customers's INTERFACE needs orders via:
          line 13: TOrder  [class]  -> move/extract this

The first block is cycles --edges, the second cycles --causes. A group with an interface edge is flagged as the one with the widest recompile blast radius; an implementation-only group is marked “legal, lower impact”.

The same cycle also shows up per file as a lint finding, which carries its own fix command:

Orders.pas:25:1  [warning] circular-uses: Circular unit dependency among 2 units:
  Customers -> Orders -- it already routes through an implementation-section uses,
  so it compiles; this is a coupling smell, not a build error. Extract the shared
  code into a new unit (moving another use to the implementation section will NOT
  break this cycle)
  fix: drag-lint cycles --fix --project <X.dproj> --unit orders
03 — In the IDE: the fix

Asking drag-lint to untangle it

There are three places to start the fix. All three run the same engine verb, cycles --fix, with the active project, its index and the IDE’s active platform. The IDE gives each such job a 120 minute limit, longer than the engine’s own limits, so the engine always times out and rolls back before the IDE would ever kill it.

Where What you click What it does
The drag-lint menu drag-lint > Uses & Dependencies > Fix Circular Uses Mechanically (dry run)... Dry run only

The engine picks the group. There is no apply from a menu click. All files are saved first, because the engine plans and compiles from disk.
The Uses & Deps tab View > Tool Windows > drag-lint, tab Uses & Deps, section This project -- Circular uses (cycles --fix) Dry run, then Apply

One row per cycle group, with Dry run and Apply buttons. Apply asks first (Yes / No, default No).
The Structure window Diagnostics tree, right-click a circular-uses finding: Fix this cycle (dry run)... or Apply cycle fix... Dry run, confirm, apply

On a cycle finding these two items replace the generic Fix it. Apply cycle fix... runs the dry run, asks you, and only then runs the apply.

Step 1: the dry run

A dry run plans the group, checks the plan against the files on disk, stages the result in a shadow tree and prints a verdict. No source file of your project is written. It does build your project once (the baseline build, see below), and that build writes what any build writes: DCUs and the exe.

The verdict is either mechanical or refused, with one line per reason. For the demo pair it is mechanical. The plan first says why the group cycles, then lists every move and every edit:

## Cycle 1: customers <-> orders
...
### Why it cycles
- `customers` interface uses `TOrder` (class) at `Customers.pas:13`; declared in `Orders.pas:10`.

### Step 1: what moves where
1. `TOrder` -- **class with methods**, declared at `Orders.pas` lines 6-19; ...
   - Recipe: **extract a base class** and keep `TOrder` where it is. Why: its method
     bodies use `TCustomer`, which live in units of this cycle; ...
   - New class `TOrderBase` in `Orders.Untangle` carries exactly what the units below
     use: nothing (an empty base).
   - `TOrder` stays in `Orders.pas` and becomes `TOrder = class(TOrderBase)`; ...
   - Units that switch to `TOrderBase` (the name is replaced on these lines):
     `Customers.pas` lines 13, 16, 30.

### Step 2: uses clauses -- keep, move or remove the old unit
- `Customers.pas` / `Orders`: nothing from it is used there any more -> **remove** it
  from the interface uses.
...
### Part B (optional): remove the implementation-only cycle too
Nothing to do: after Part A no cycle remains among these units.

Fix it (mechanical, compile-gated):
  dry run : drag-lint cycles --fix --project <your.dproj> --db ... --cycle 1
  apply   : drag-lint cycles --fix --project <your.dproj> --db ... --cycle 1 --apply
  cuts    : the INTERFACE coupling of this cycle (Part A: extract base classes into new leaf units)
  requires: the project builds with 0 errors before the fix (the dry run checks this)

Verdict: mechanical (dry run; add --apply to write)
Shadow tree: ...\draglint_cyclefix_49108\ (deleted at exit; --shadow-out keeps it)
compile: baseline 1.4 s

Real dry run on a copy of the demo pair with a small project file added, exit code 0, trimmed where the ... are. Customers only keeps orders in a TArray field and takes one as a const parameter; it reads none of TOrder’s members. So the plan extracts an empty TOrderBase into a new leaf unit Orders.Untangle, makes TOrder descend from it, and switches FOrders to TArray<TOrderBase>. After that Customers needs nothing from Orders.

Part B cuts one edge of a group that is already implementation-only. This is the three-unit group from the repository’s larger circular-demo project (cycle 3 of its three groups, chosen with --cycle 3):

Fix it (mechanical, compile-gated):
  dry run : drag-lint cycles --fix --project <your.dproj> --db ... --cycle 3
  apply   : drag-lint cycles --fix --project <your.dproj> --db ... --cycle 3 --apply
  cuts    : demoblueprint -> demoblueprint.viewmodel (routine-call inversion) (chosen)
  requires: the project builds with 0 errors before the fix (the dry run checks this)

Verdict: mechanical (dry run; add --apply to write)
Shadow tree: ...\draglint_cyclefix_21344\ (deleted at exit; --shadow-out keeps it)
compile: baseline 1.3 s

Exit code 0. Above this block the dry run prints the whole plan: why the group cycles, which edge it cuts, every edit as current text and new text.

Step 2: what you accept or refuse

The apply confirmation is built from the dry run’s result. It names the units of the cycle, the recipe and the edge it cuts, how many files will be edited, the names of any new units (or “none”), the baseline build status and time, and what happens if the build fails. The default button is No; answering No leaves the files untouched and the note reads “cancelled -- nothing written”.

Two further things can stop an apply before it starts. The IDE refuses to apply while any file the plan edits has unsaved changes (the apply rewrites those files on disk and reloads the buffers, which would drop your edits). And a refused verdict has no Apply at all: the fix is simply not offered.

What you accept with Yes is bounded. Every file the fix touches is backed up as <file>.BCK<n> with a recovery.txt; the project is built in place; and if that build fails, every file is put back. You can also refuse by choosing a different group: one run fixes one circular group, and the text output ends with one line naming each group it did not plan.

Step 3: the apply, on a copy

We ran the apply on a scratch copy of circular-demo:

The apply on a copy of the demo pair reported Applied: 5 file(s) written, 1 new; compile ok and Verified: the new unit is Orders.Untangle.pas, the other four are the two units, the .dpr and the .dproj. The re-indexed cycles then printed No circular unit dependencies found.

04 — Under the hood: finding and choosing

Which cycle, and which edge

Finding the cycles

The index records every unit’s uses entries, tagged interface or implementation. A “cycle” in the report is a strongly connected component of that graph, not a ring: two loops that share a unit form one group, and the report draws the edges that exist rather than inventing a traversal order. Each group is classified by its edges:

  • Interface-coupled: at least one unit uses another in its interface. Widest recompile blast radius, so it comes first.
  • Implementation-only: legal, lower impact, optional to fix.

Two parts

The fix is split to match. Part A removes the interface coupling: it turns an interface-coupled group into a legal implementation-only one. Part B then cuts one edge of what remains. --part a or --part b asks for one; --part all applies A, re-indexes and re-plans, then applies B, in one run (it needs --apply).

Choosing the edge

For Part B the engine evaluates every edge of the group and weighs the recipes in a fixed order: move globals, then routine-call inversion, then member hand-over, and last, when the consumer needs a class of the cycle, a base class extracted for that class (section 05). Within one recipe the edge whose surface has the fewest members wins, then the one with the fewest references. One edge is cut per run, and every other edge keeps its reason for not being cut. On the three-unit group the plan prints exactly that:

- demoblueprint -> demoblueprint.viewmodel: recipe: routine-call inversion -- cut by this plan
- democontrolplan -> demoblueprint: not mechanical: TDemoBlueprint (class): its method
  bodies use DemoBlueprintViewModelCreate, which live in units of this cycle --
  they would have to move with it
- demoblueprint.viewmodel -> democontrolplan: not mechanical: TDemoControlPlan (class):
  its method bodies use TDemoBlueprint, which live in units of this cycle --
  they would have to move with it
05 — Under the hood: the recipes

What the engine actually edits

Part A: move declarations into a leaf

Enums, records, constants and variables that tie the cycle together move, unchanged, into a new leaf unit named <Declaring>.Untangle (or an existing unit that is still a leaf). Each consuming unit then gets a uses decision: keep the old partner, move it from the interface uses to the implementation uses when only the implementation still needs it, or remove it when nothing else from it is used. A class whose method bodies use the cycle is not moved. A base class carrying just the members the other units read is extracted into the leaf instead, and those units switch to it — but only where every use of the class is a member read, a nil test or Assigned, Free or FreeAndNil, or an assignment to or from another place that switches too. Such places are a const or value parameter, a local variable (in a var section, an inline var, or for var L: TX in), a plain field that is not published and not used outside its unit, an array field (TArray<T> or array of T) that is only sized, stored into and read from, and a TList<T> or TObjectList<T> field used only through Create, Add, Insert, Remove, IndexOf, Contains, Delete, Clear and Count. A property the other units read through a getter method takes that method along: it becomes virtual; abstract; in the base and override; in the class. When nothing is read the base is empty, as for the demo pair. Any other use (a cast, a var parameter, a function result, another type argument, a getter that already carries directives) refuses with base-class and names the line. Part B uses the same base class as its last resort; there a type test X is TX and a read through a cast, (X as TX).M, switch to the base as well.

Part B, recipe R1: routine-call inversion

When an edge is made of routine calls and every type in the routines’ signatures is declared outside the cycle, or is a plain type of the cycle (an enum, a record, an alias) that can move out of it, the consumer calls each routine through a procedural variable declared in a leaf. Those plain types, and any movable globals on the same edge, move into that leaf first. The declaring unit assigns all the variables in one edit of its initialization section, and a consumer line that calls several of the routines is rewritten once. A call qualified by the unit name (B.Foo(...)) and a routine assigned as a value (X := Foo) are redirected the same way; taking the routine’s address (@Foo) refuses. This is the real before and after for DemoBlueprint:

{ DemoBlueprint.pas -- before }
implementation
uses
  DemoBlueprint.ViewModel; // <-- the edge to cut: used for ONE routine call
...
  FViewModel := DemoBlueprintViewModelCreate(FFolderId);
{ DemoBlueprint.pas -- after }
implementation
// <-- the edge to cut: used for ONE routine call
...
  FViewModel := DemoBlueprintViewModelCreatePtr(FFolderId);

{ DemoBlueprint.Interfaces.pas -- the leaf gains }
  TDemoBlueprintViewModelCreatePtr = function(const pFolderId: Integer): IDemoBlueprintViewModel;
var
  DemoBlueprintViewModelCreatePtr: TDemoBlueprintViewModelCreatePtr;

{ DemoBlueprint.ViewModel.pas -- the declaring unit gains }
initialization
  DemoBlueprintViewModelCreatePtr := DemoBlueprintViewModelCreate;

The signature is copied verbatim, every const and parameter name included. A comment that sat on the removed uses line stays behind as a lone comment.

Part B, recipe R2: member hand-over

When an edge is only is / as checks against one class plus reads of its members, plain assignments to them, or calls of its instance methods inside with X as TClass do, the class implements an I<Class>Surface interface declared in its leaf, and the consumer goes through Supports / as on the interface. A member the consumer assigns becomes a read/write property with a one-line setter Set<Name>; a method becomes an interface method with its signature copied verbatim, and a virtual method still dispatches to its override. An indexed property is carried for reading, its index list copied verbatim. If the leaf already declares an I<Class>Surface, an identical one is reused and a different one makes the new interface take the lowest free number suffix; a getter Get<Name> the class already has is reused when it is exactly function Get<Name>: <T>; and the property reads through it.

06 — Under the hood: the safety net

Shadow tree, compile gate, atomic apply

Is the project clean to begin with?

Before anything is staged, the baseline build runs on your untouched project (msbuild /p:Config=Debug, for the platform you name; the IDE passes its active one). If it does not build, the verdict is dirty-baseline, nothing is written, and the fix is not offered. One exception: a baseline that fails only with F2047 on a unit of the Part A group being fixed is planned anyway, and the build after the edit is the proof. The Release configuration is never built.

Can the plan be applied to the files exactly as they are?

The plan is checked against the files on disk and staged in a shadow tree (C:\TEMP\draglint_cyclefix_<pid>\ by default, deleted at exit unless a message of the run cites a file in it; --shadow-out <dir> keeps one). A file that changed after it was indexed gives stale-file (on --apply the engine first re-indexes once and plans again); a line that is not what the planner saw gives anchor-mismatch.

Does the result compile?

On --apply the backups are made, the edits are written and the project is built in place. One bounded repair is allowed on a compile error (R4: a cast through the plan’s ancestor, a missing leaf unit in uses, a re-emitted pointer type); anything else, or a second failure, rolls every file back.

Did it do what it said it would?

The project is re-indexed (unless --no-reindex) and cycles is run again. Its output must equal the plan’s prediction, or the result is reported as written but not verified. An apply that skips the compile is refused outright (--apply --no-compile is exit 2).

The write is all-or-nothing. A write or build that fails part-way ends with every file restored byte for byte, or, if the restore itself fails, the failure named. One caveat is stated in the engine’s own docs: a rollback restores your sources, but not the DCUs the failed build wrote, so rebuild the project after a rollback before you trust its output.

0exit: written and verified
1exit: refused, rolled back, or unverified
2exit: error (bad flags, failed write or build)
07 — Under the hood: the refusals

What it will not do, and why

The engine never guesses. Every refusal prints as Verdict: refused with one line per reason, and the kinds fall into a few families:

Family Examples Why it stops
The run and the gate dirty-baseline, compile-error, build-timeout, no-compiler, stale-file, anchor-mismatch, outside-roots, non-ascii-text (and the exit-2 pair build-error, write-failed) Unsafe to write

None of these judges your code; each names a condition the proof needs. dirty-baseline: the project does not build before any edit, so a failure after the edit could not be attributed to it. The one exception is a baseline that fails only with F2047 on a unit of the Part A group being fixed: that group is planned anyway, and the build after the edit is the proof. compile-error and build-timeout: the build after the edit failed, or did not finish inside the limit; every file was rolled back (rebuild before trusting the DCUs). stale-file and anchor-mismatch: a touched file is not the file the index saw. --apply re-indexes once and plans again; a dry run, --apply --no-reindex, or a file still stale after that re-index refuses — re-index and run again. outside-roots: the plan would edit a file outside the project’s own roots, shared code the gate cannot prove for the other projects that use it. non-ascii-text: a moved line holds a character the target file’s ANSI encoding cannot carry. A new unit the fix creates is written as UTF-8 with a BOM instead, so only an existing ANSI file refuses. no-compiler: no RAD Studio build environment was found; name one with --rsvars <rsvars.bat>, or skip the build in a dry run with --no-compile.
The plan base-class, blocked-symbol, directive, uses-in-include, unresolved-edge, edge-still-used, manual-edit A human decision

base-class: a class whose method bodies use the cycle cannot move, and a base class can stand in for it only where every use reads a member, tests for nil, frees the object or hands it to another place that switches too: a parameter, a local variable, a plain unpublished field, an array field or a TList / TObjectList field (section 05); any other site — a var parameter, a function result, a cast (apart from Part B’s is test and read through as), another type argument — is named with its line. blocked-symbol: the declaration itself cannot move (a routine, a class that inherits or is generic, a block the planner does not recognise). directive: a conditional directive ({$IFDEF} and its kin) surrounds an edited uses entry, or the edit would cross one; only the active branch is indexed and built. {$REGION}, {$WARN}, {$HINTS} and {$MESSAGE} inside a uses clause are kept byte for byte and do not refuse. uses-in-include: the uses clause lives in an {$I} include that other units may share. unresolved-edge: the interface section names the other unit but uses nothing from it that the index records. When nothing else explains it, the plan now moves the entry to the implementation uses, or removes it if nothing uses it at all; the refusal remains only when a text search still finds an identifier of the other unit there, and it names that identifier and line. edge-still-used: after the cut the consumer would still use the other unit for another name, so the uses entry, and with it the edge, would stay (a call to an inherited member of the same name no longer counts). manual-edit: the text around an edit has a shape the planner does not rewrite, such as a class heritage list whose parentheses never close; indented type / var / const headers, the one-line forms var GX: T = v; and type TR = record, and a heritage spread over several lines are handled.
R1, routine-call inversion overloaded-routine, signature-in-cycle, init-order, duplicate-identifier Order and linking matter

The pointer is assigned in the declaring unit’s initialization section, so every call must run after that: init-order refuses a call made from, or reachable by name from, the consumer’s own initialization section. signature-in-cycle: the procedural type lives in a leaf, which cannot name a type of the cycle; a plain enum, record or alias moves into the leaf with it, so only a class whose method bodies use the cycle still refuses. overloaded-routine: the index binds a call by name, so the signature copied into the pointer type could be another overload’s. The routine is still inverted when the argument counts settle it: the overload the index bound accepts every call’s argument count, no other overload accepts any of them, and none has a default parameter. duplicate-identifier: the leaf already declares the pointer’s names differently and every numbered variant up to 99 is taken. An identical declaration is simply reused, and a different one makes the new pointer take the lowest free number (FooPtr2, FooPtr3, …). Linking is handled, not refused: if the declaring unit is used only by the consumer and the .dpr does not list it, the linker would drop it after the cut, its initialization would never run and the call would be a nil call at run time, so the plan adds <Unit> in '<path>' to the program’s uses (and a DCCReference to the .dproj when it is missing).
R2, member hand-over member-write, member-unsupported, construction, class-method, with-member, ref-counted, exception-semantics The interface is not enough

The extracted interface carries properties (read/write with a setter where the consumer assigns them) and the instance methods the consumer calls inside with X as TClass do. member-write: the consumer writes a member in a way a setter cannot carry — Inc or Dec on it, passing it to a var or out parameter, or writing into a record-typed member. member-unsupported: a member the interface cannot carry — one the class inherits rather than declares, a default indexed property, or a write to an indexed one. construction: it creates the object, which needs the class. class-method: it calls through the class name, a class method, a method pointer or an overloaded method, or a method whose signature names a type of the cycle. with-member: a name inside a with X as TClass do body would bind to something else once the subject is an interface. ref-counted: the class counts references (a TInterfacedObject), so releasing the temporary interface of as or Supports would free the object. exception-semantics: a failed as ISurface raises EIntfCastError where as TClass raised EInvalidCast, and the consumer handles EInvalidCast without an is guard on that cast.
What stays manual

A refused group is yours. --plan still prints the playbook and the standard remedy for it, and the repository ships a script that applies a playbook’s edits literally if you decide to follow one by hand. Moving a class whose method bodies use the cycle, creating objects through an interface, and any cut a refusal names, stay human decisions. Every refusal line names the symbol, file or line it stopped at: that is where the hand edit starts.

08 — Limits

Honest edges

  • It builds your project. A dry run costs one full build; an apply costs up to three (baseline, after, one repair). On a 625-file Micronite client project that meant a dry run of about two minutes. --no-compile skips the build in a dry run only.
  • One group per run. With no --cycle or --unit, the first mechanical group is planned and the rest are named, not touched.
  • Part A does not always remove the cycle. It removes the interface coupling; what can remain is a legal implementation-only group for Part B. On the demo pair nothing remains, and the plan says so before it writes anything. Moving a uses entry to the implementation section alone would not have broken that cycle, as the lint message says.
  • Some shapes have no recipe (inheriting classes, class-reference arguments, and an interface uses entry whose use a text search finds but the index cannot explain). They are printed with their reason and the standard remedy, and the engine says it cannot help.
