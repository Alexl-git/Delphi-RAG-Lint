## What is worth noticing in that output

**It names the exact symbol that forces each edge, not just the unit pair.** "DemoLogger
depends on DemoSession" is easy. Saying *why* -- `TDemoSession`, a class, referenced at
`DemoLogger.pas:40`, declared at `DemoSession.pas:20` -- is what makes the cycle actionable.

**It reports three edges, not four.** The project has a four-unit cycle:

```
DemoConfig  -> DemoLogger    interface
DemoLogger  -> DemoSession   interface
DemoSession -> DemoAudit     interface
DemoAudit   -> DemoConfig    IMPLEMENTATION  <-- why this compiles at all
```

"Why it cycles" lists only the three **interface** edges, because those are the ones that
constrain compilation and the ones Part A breaks. The implementation-level edge is what makes
this legal Delphi -- a cycle closed entirely through interface uses would not compile
(`F2047`).

**It picks a different recipe per symbol, and says why.** The two enums (`TDemoLogLevel`,
`TDemoAuditKind`) have no code of their own, so they simply move into new leaf units. The
class `TDemoSession` does NOT move: its method bodies use globals that live in units of this
very cycle, so moving it would drag those bodies -- and everything they use -- along. Instead
the report extracts a base class, `TDemoSessionBase`, carrying exactly the members the other
units use (`FId`, `FUser`, `Id`, `User`), and switches those uses to it. That single decision
is the difference between the failed run and the passing one.

**Every edit is spelled out as current text and new text,** every uses clause gets a
keep / move / remove verdict with the lines that justify it, the full text of each new unit is
given, and the `.dpr` / `.dproj` registrations are included. Nothing is left to judgement.

**It defines DONE, and says what will NOT be gone.** After Part A the four units still form a
cycle -- through implementation uses only, which is legal and cheap. The checklist ends with
the exact `cycles` output to expect, so "did it work" is a comparison, not an opinion. Part B
(optional) explains which of the remaining edges are mechanical to cut and which are not, and
why.

**It tells you what each compile error would mean** -- E2003, E2065, E2010/E2033, F2047,
F1026 -- and the fix for each, because the index can miss a reference (for example a `set`
type) and the compile is the final check.

## The globals, and why they matter here

Seven module-level globals are shared across unit boundaries, each touched by at least two
units:

| Global | Declared in | Written by | Read by |
|---|---|---|---|
| `GDemoSettings` | DemoConfig | DemoConfig | DemoAudit |
| `GDemoMinLevel` | DemoLogger | DemoConfig | DemoLogger, DemoConfig |
| `GDemoLogCount` | DemoLogger | DemoLogger | DemoConfig |
| `GDemoSessionCount` | DemoSession | DemoSession | DemoLogger |
| `GDemoActiveSession` | DemoSession | DemoSession | DemoLogger |
| `GDemoAuditCount` | DemoAudit | DemoAudit | DemoSession |
| `GDemoAuditTrail` | DemoAudit | DemoAudit | DemoSession |

Shared mutable globals are what make a cycle like this painful in practice: they create
ordering dependencies between units that the compiler will not complain about. They are also
exactly what the report's Part B works on -- moving the shared variables (and the plain types
they need) into a leaf unit is the standard remedy for the implementation-only cycle that
Part A leaves behind.
