## What is worth noticing in that output

**It names the exact symbol that forces each edge, not just the unit pair.**
"DemoLogger depends on DemoSession" is easy. Saying *why* -- `TDemoSession`, a
class, referenced at `DemoLogger.pas:40`, declared at `DemoSession.pas:20` --
is what makes the cycle actionable. That is the difference between a warning
and a fix plan.

**It reports three edges, not four.** The project has a four-unit cycle:

```
DemoConfig  -> DemoLogger    interface
DemoLogger  -> DemoSession   interface
DemoSession -> DemoAudit     interface
DemoAudit   -> DemoConfig    IMPLEMENTATION  <-- why this compiles at all
```

drag-lint lists only the three **interface** edges under "Why it cycles",
because those are the ones that constrain compilation and the ones you have to
break. The implementation-level edge is exactly what makes this legal Delphi --
a cycle closed entirely through interface uses would not compile. So the tool
is not merely detecting a loop in a graph; it is distinguishing the edges that
matter from the edge that makes the loop survivable.

**The fix it proposes is the right one for this shape.** All three offending
symbols are type declarations (`TDemoSession`, `TDemoLogLevel`,
`TDemoAuditKind`). Extracting them into leaf contract units removes every
interface edge without touching behaviour.

## Honest caveats
