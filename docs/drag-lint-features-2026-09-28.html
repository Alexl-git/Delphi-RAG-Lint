What it is. drag-lint is an AST-exact symbol index, linter and refactoring engine for Delphi / Object Pascal. It parses your code with tree-sitter into a SQLite index, then answers questions about it -- symbols, callers, types, dependencies, documentation -- without a compiler and without the IDE having the project open. The Component Converter is a rules-driven system built on that index for migrating legacy VCL components to modern replacements.

The round trip of one field, as a text trace (round-trip, the 26th question)

Select a grid column or other data-bound control, a TField variable, or a TABLE.COLUMN, and the new question follows that value from its data anchor both ways through the client-server pipe: the WRITE path (event handler -> sender -> pipe -> server dispatch -> apply -> column -> response) and the READ path (fill -> pipe -> server query -> back), plus every other route that reaches the same anchor. It reads three indexes at once -- the client project, the server project and the SQL-script index -- and answers in text: a numbered, anchored trace (trace.dlgraph, Form A) shown in the bundle's index.html. A chart drawn from the text is the next step.

  • Conditions are quoted, not paraphrased. Each guard is read from the source file (which must still match the index) and written as WHEN "..." or UNLESS "...": an if condition verbatim; a try/except guard as its statements plus a generated raises; a case as its header.
  • A hop the index cannot make is a numbered STOPS, counted as unresolved and saying why -- never a guess. A direction that stops early names every tier it did not reach, and the title claims only the directions it walked.
  • Measured. The grid column for OPERAT.NAME on ORM3: 76 steps, 31 conditions, 4 process-boundary crossings, 2 unresolved; 17 of 17 nodes of a hand-built reference trace matched and 12 of 12 guards. A second field the owner checked by shape (MSCLIST.NUM): 103 steps, 35 conditions, 4 crossings, 2 unresolved. The 2 unresolved are the SQL statement texts, which live in database rows the index does not hold.

A calculated field says so, and offers its sources

A control bound to a calculated field (one the dataset's OnCalcFields handler writes) has no column to reach. Its trace now stops at the anchor with the title "Why ... cannot be traced -- it is calculated", names where the field is created and computed with the handler's own guards, and adds a DERIVED section: one numbered row per field the computation reads -- including the fields that choose the value in a case selector or in the condition of an if around a write, marked "chooses the value" -- each with a ready command that traces that field instead. A value the walk cannot map (a local set in several places, a parameter) is a named row with no command, never a guess. Measured: the FtrName grid column offers 18 source fields; Tolerance 4 fields and the 2 case selectors that choose its value; InspAsVarStr, whose every write is a constant, the 2 fields its ifs test. Running one row's command end to end traces MSCLIST.DIMABBR in 98 steps.

A click on a chart opens the line in RAD Studio; one command for AI agents

Every row of a chart, and every @File.pas:line anchor of a round-trip page, is a draglint:// link that opens the line in the running IDE, once a small link handler is registered for the user (chapter 12). The handler treats every link as hostile until checked: it opens only a local Delphi source file, never a network path, a project or package file or anything else, and with no IDE running it shows the file in Notepad rather than starting the file's default program. Measured: 126 of 126 anchors of the OPERAT.NAME trace are links.

For an AI agent, charts\src\Ask-Report.ps1 asks any chart question with one command: it finds the project's index with the engine's resolve-dbs, takes the server and SQL indexes from a pairs file, refuses a stale index with the reindex command (it never indexes), and prints the answer as anchored text. Why it exists: in a side-by-side run on one data-path question (one run per method, indicative only), an agent that ran the round-trip question first used 6 tool calls and about 77,000 tokens and got 19.5 of 20 key facts, against 26-33 tool calls, about 122,000 tokens and 16.5-17 facts with text search or index queries alone -- yet an agent told about the questions still skipped them because setting up the three index paths looked like more work than searching. The wrapper removes that setup.

Calls on unit-level variables now bind (resolver 1.11.0-alpha, 1.20.0)

A call such as GDatasetsDef.GetTable(...) on a unit-level var, or on a field reached from a nested routine, used to have no target. The receiver typer now walks the class chain, then exactly one visible unit-level variable, before trying the name as a type. Measured on copies: ORM3 SERVER +42 bindings, CLIENT +184, DataCopy +56, YADF 0 -- and 0 bindings lost or moved on any of them. A re-resolve, not a re-parse (about 1 minute per ORM3 project index).

Self.FField := X is a write (extractor 1.20.0-alpha, 1.19.0)

The extractor recorded the member of every Self.X as a read, whichever side of := it sat on, so find-callers --resolved listed writers as readers and the who-writes chart under-reported. It is now a write, and an explicit Self.X write binds the member rather than a same-named local. SQL column symbols also sit on their own line now (a column written on its own line was one line early). Because extraction changed, every index re-parses once.

1. Indexing and the code database

  • AST-exact indexing via tree-sitter grammars for Pascal and DFM -- no regex, no string-literal or comment noise.
  • One database per project, stored beside the project in _D-RAG\, plus per-platform library indexes for the RTL/VCL and third-party code.
  • Compile-closure indexing -- a project index contains exactly what the compiler sees: project members, transitively used project-local units, each unit's sibling .dfm, and its {$I} includes. Loose unreferenced files stay out.
  • Build-accurate conditional compilation -- the define profile is read from all four MSBuild property groups (base, configuration, and the per-platform variant of each), so the branches indexed are the branches compiled.
  • Generics by arity -- generic types and methods are indexed under their bare name with their parameter list; ancestry resolves by parameter count, so a generic base is never confused with a same-named non-generic class.
  • Library and browsing-path scans read the IDE's own registered paths (Win32 + Win64, or every platform including Android / iOS / Linux / macOS).
  • Incremental re-indexing with per-file fingerprints -- only changed files are re-parsed; interrupted runs resume rather than restart.
  • Resolve-only mode re-derives call edges, ancestry, helper targets, member and enum-value bindings and purity verdicts from parses the index already holds, skipping the file walk entirely.
  • Watch mode re-indexes on file change at a configurable interval.
  • Cross-database resolution -- a project index can consult a library index for calls it cannot resolve locally, without ever inventing an edge.
  • Parallel indexing across configurable job counts, driven by a named manifest so a whole estate rebuilds with one command.
  • Project registration and reconciliation -- add a project to the manifest, and sync its .dproj / .dpr member list against the units it actually uses.
  • Full-text index (FTS5, unicode + trigram) over source text, comments, DFM content and SQL.

2. Search and navigation

  • Symbol lookup by name, qualified name, or substring -- exact, fuzzy and case-sensitive modes, filterable by symbol kind. A forward declaration is folded into its real declaration.
  • Find callers / find callees for any routine, method or event handler, with surrounding source context. With --resolved, precise per-target answers now cover properties and fields (read / write) and enum values (read).
  • Which unit declares this? -- resolves a symbol to the unit you need to add to a uses clause.
  • What implements this interface? -- hovering an interface lists the classes that implement it and, separately, the interfaces that extend it.
  • Type-at-position -- resolve the identifier at a file/line/column.
  • Text, message and caption search across .pas, .dfm and .sql -- string literals, DFM captions, SQL exception text and comment prose, with exact-phrase, any-order and substring matching.
  • Declaration-clause search -- finds declarations by clauses the index does not model (stored IsFontStored, default 0).
  • Unit outline -- every type, method and its line, without opening the file.
  • List every symbol of one kind (new) -- query --kind <k> --all, for example every unit in a database, with no row cap.
  • Where-used / usages reporting across the whole indexed estate.
  • Concept lookup -- routes a human phrase ("the scheduler", "delta streaming") to the owning symbol via topics authors write in ordinary /// comments.

3. Dependency and architecture analysis

  • Circular-dependency detection with generated cycle reports that explain why a cycle exists and recommend a fix.
  • Uses-clause audit and auto-fix -- unused units, misplaced interface/implementation entries, missing units.
  • Impact analysis -- the transitive blast radius of a symbol, by depth.
  • Interface-edit impact before the build -- lint-tree reports every dependent reference an edit to a unit's interface would break, now including removed properties, fields and enum members.
  • Call graph and butterfly view -- callers and callees composed into one navigable chart (DOT, Mermaid, text or JSON).
  • Reverse call tree to arbitrary depth, and the shortest resolved call path between two routines.
  • Effect analysis -- which routines are proven free of side effects across the whole call graph, and, for the rest, a one-line witness saying why.
  • Third-party dependency reporting -- what your code pulls in from where.
  • Spring4D dependency-injection wiring -- interface to implementation class, lifetime, and resolve sites.
  • Class surface and code slices -- the public interface of a type, or a minimal self-contained compilable slice.
  • Type hierarchy -- ancestors (with generic type arguments), descendants and class helpers.

11. Component Converter

A rules-driven system for migrating legacy components (for example Orpheus TOvc* controls, or BDE data access) to modern replacements such as DevExpress or FireDAC -- across every surface a component touches, not just the declaration.

Conversion rules language

  • A documented DSL with 13 directive kinds, a superset of the reFind format -- covering type conversion, property and event linking, defaults, notes, unit add/remove/swap, regular-expression rules, and reusable named value mappings.
  • Property and event linking between source and target components, including value casts where the two components express the same idea differently.
  • Whole-object links -- linking two properties of the same class (Font to Font) carries every sub-property the form streams; when the classes differ, every leaf must still be named, because an invented target path is how a form stops loading.
  • Reusable value mappings with conditional branches, so an enum or a set of related properties translates once and is applied wherever needed.
  • Tagging -- rules can be labelled so a single rule book serves several migration jobs.
  • Validation against reality -- every referenced property path is checked against the real property tree of the real class in the index.

Conversion engine

  • Rule scaffolding -- generates a valid, ready-to-edit rule file from the actual property trees of the source and target classes.
  • Five-surface rewrite -- declaration type, uses clauses, the .dfm, every property and event access site in code, and runtime construction sites.
  • Value and class casts realised -- a cast with a code template is applied at every access site; a cast found without a template, and a cast not found at all, are reported as two different problems because they need two different fixes.
  • Image payloads carried, never silently dropped -- the image format is sniffed from the bytes; a format the target accepts is carried verbatim, anything else is reported as a warning naming the instance, the property, the format found and the formats accepted.
  • Unlinked-property warnings -- a source property that no rule carries is reported once per type as "dropped on N of M converted instances"; a minority count, the controls somebody deliberately styled, is the stronger signal.
  • Graphics census -- glyph-vacuum decodes every streamed graphic under a folder tree and writes per-instance and per-class tables plus a visual gallery, as the measured input to glyph rules.
  • Dry run by default, backups and a recovery file on every write, selective application to named components, and a machine-readable remainder as typed JSON items.
  • Cast library -- shared value-translation blocks reused across rule books.

Rule editor (ConvRulesEditor)

  • Visual rule authoring -- a Windows desktop application that turns rule writing into a mapping exercise rather than text editing.
  • Three-column mapping grid -- source properties, assigned targets, and the pool of unassigned targets -- with assign, unassign and double-click in place.
  • Completion tracking, real property trees from the index, auto-match, class pickers, mapping and curation editors, a rule catalog, a raw DSL view, validation on save, and light and dark themes.
  • Form-driven and unit-driven workflow -- open a real .dfm, or any .pas even if no project lists it; the Unit Rules tab lists each used unit and the section it is declared in.
  • Class list with state -- checkboxes, origin marks and three states (ruled, skipped, open), a progress line, and partial-name search; a unit's classes come from an on-demand scratch index, so a unit outside every project still lists its classes.
  • Named filters and "do not convert" marks -- mark classes in bulk; the marks persist beside the rules.
  • Several rules per source class -- legal across rule books, with a chooser on double-click; only a collision inside one book warns.
  • Trustworthy "already used" marks -- a property is marked used in code only on a receiver the form file names as an instance of that class, and never from a comment; what the filter rejects is listed with the reason rather than hidden.
  • Pinned engine with a drift check by content hash, not version string.

12. Diagrams and charts READY

26 of the 27 catalogue questions about a codebase can now be answered from the index: who calls this, who writes this field, what does this form wire, where does this protocol command go -- and, new in this edition, the full round trip of one edited field. Twenty-five answer with a picture; round-trip answers with an anchored text trace. Every box, row and step is a fact from the index with a file and a line behind it -- nothing is drawn from prose or guessed, and a hop the index cannot make is shown as a stop. Only compare (before / delta / after) is not built; the owner has parked it.

How a question is asked. A question is one formal call: a question, a selection (a method, a field, a type, a unit, a form control, a table column...) and a few parameters (depth, caps). Today it is asked with the charts script New-DiagramArtifact.ps1 -Question <id> -Target <selection> -DbPath <db>, which reads the index through the engine's own verbs and lays the result out with Graphviz 16.1; round-trip adds -ServerDbPath and -SqlDbPath. The same dispatch becomes one engine verb, ask, when the tool-set moves into the engine (Appendix A.3). The script runs against frozen copies of the indexes, so a chart's counts are reproducible. (new) Ask-Report.ps1 -Question <id> -Target <selection> -Project <x.dproj> asks the same questions in one command on the live indexes -- it resolves every index itself, stops on a stale one with the reindex command, and prints the answer as text: the whole trace for round-trip, otherwise one name @File.pas:line line per chart row, with a note when the chart drew fewer rows than it counted.

What comes out -- one folder per answer: an HTML page that opens in any browser; for a chart, an SVG whose rows are real links, PNG and PDF exports and the Graphviz .dot source and layout geometry from the same run; for round-trip, the trace itself (trace.dlgraph); and in both cases a meta.json recording the index fingerprint and the command that regenerates the folder, and a ready-to-paste DocInsight <remarks> cross-reference, so a unit's documentation can point at its chart.

Viewing a chart and jumping to the source. A chart opens in a web browser; there is no chart viewer inside RAD Studio. (The IDE's docked "drag-lint Graph" window hosts the separate call-graph viewer and does not open chart folders.) Each row of a chart, and each @File.pas:line anchor of a round-trip page, links to draglint://open?file=..&line=.. (an anchor whose file the indexes hold at no path or at several stays plain text). A click hands the link to a small handler, which writes the file and line to the drag-lint IDE plugin's named pipe, \\.\pipe\drag-lint-open-source; the plugin opens the file at that line in the editor. It needs the plugin installed and RAD Studio running; with no IDE answering within one second, the handler shows the file in Notepad (the line is not positioned), never with the file's default program.

One-time registration, per user, no administrator rights: Register-DragLintProtocol.ps1 copies the handler to %LOCALAPPDATA%\drag-lint\Open-DragLintUri.ps1 and writes one key, HKCU\Software\Classes\draglint, whose command runs that copy with a PowerShell path that survives an update (%ProgramFiles%\PowerShell\7\pwsh.exe, else the Store alias, else Windows PowerShell 5.1; never a versioned package folder). -DryRun prints the exact command it would write and touches nothing; -Unregister removes the key and the copy. It refuses to register a handler from a work-in-progress worktree unless forced, so after the merge it is run once from the main checkout: C:\Projects\Delphi-RAG-lint\charts\src\Register-DragLintProtocol.ps1. A registration made before 28 September points at the worktree and at a versioned PowerShell folder, and must be redone.

What the handler will and will not open. Only a file on a local drive path (X:\...) with a source extension, .pas .dfm .dpr .inc .sql .fmx. It refuses network and device paths, NTFS streams, wildcards, reserved device names, project and package files (.dproj, .groupproj, .dpk), a line that is not ASCII digits, a key given twice, and anything but exactly one argument -- all before it touches the file or the pipe. A refusal exits 2 and writes one line, capped at 512 characters, to %LOCALAPPDATA%\drag-lint\uri-handler.log. Stated limits. who-writes / who-reads may undercount in legacy code that uses with heavily, because with scope is not modelled. wiring on a client project sees few registrations (4 on ORM3 CLIENT against 535 on SERVER). round-trip: a guard sees only the innermost enclosing if of its exit (E1); the texts of the SQL statement for a posted row and of the SELECT are not in the indexes (E4), so both are STOPS; a direction that stops early notes every tier it did not reach.
