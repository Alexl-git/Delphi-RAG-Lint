Feature list · release 1.13.0-alpha · 16 September 2026
Supersedes the 9 September 2026 edition. Every number below was read from the engine on the day of writing, not carried over from the previous document.

What this is. drag-lint reads a Delphi codebase the way the compiler does -- it parses the real syntax rather than searching for text -- and stores what it learns in a database beside the project. Everything else in this document is a question that database can answer in under a second, on a codebase too large to hold in your head.

It is a command-line engine, an IDE plugin for RAD Studio, and a language server. The same answers reach all three.

1. Indexing and the code database

One database per project, kept beside the project file. Rebuilds are incremental: only what changed is re-read.

  • Indexes Pascal source, form files (.dfm) and SQL together, so a question can cross from code to a form to a table.
  • Knows a project's real membership -- the units it actually compiles, not whatever happens to sit in the folder.
  • Reports when it is out of date rather than answering from stale data.
  • Reconciles a project file against the units it really uses, and can repair it.

2. Search and navigation

Exact answers, not text matches. No hits from comments, string literals or stray backup copies.

  • Where is a symbol declared; what is its signature.
  • Who calls it -- and who calls them, to any depth.
  • Which unit declares a type, so it can be added to a uses clause.
  • Full-text search across messages, form captions and SQL exception text.
  • What implements this interface -- new in this release; see chapter 12.

3. Dependency and architecture analysis

  • Circular unit dependencies, with a followable plan for breaking them.
  • Blast radius: everything a change to one symbol could reach.
  • Third-party dependency rollups.
  • Dependency-injection wiring and form event wiring, including registrations that never resolve.
  • A type's deep property tree, following into class-typed properties.

4. Linting and auto-fix

181 rules in 16 categories. 23 fix themselves.

  • Bug patterns, resource-leak shapes, exception-handling mistakes, naming, dead code, documentation gaps.
  • A reviewed finding can be marked as accepted, with the reason recorded in the code -- so the next report is quiet about it and the reasoning survives.
  • Rules can run for one file or a whole project; some questions only exist at project scope.

The standard this is held to. A finding count in the thousands is treated as a defect in the rule, not a fact about the code. The point is that when a message appears, it means something.

5. Compiler-less diagnostics and compile checking

  • Catches missing-unit and undeclared-identifier problems without a full build.
  • Can check an unsaved editor buffer.
  • Imports a real build log and lines its errors up with the code.

6. Documentation

  • Generates documentation comments for a symbol, a unit or a whole project, in Delphi's own format.
  • Records facts it can prove -- who calls this, what it raises, what it reads and writes, how complex it is, which tests cover it.
  • Hand-written prose is preserved; only the generated part is refreshed.
  • Flags documentation that has drifted away from the code it describes.

7. Refactoring and code actions

  • Rename a symbol across the project.
  • Safe-delete, with a check for what would break.
  • Extract a method; turn a public field into a property.
  • Clean up uses clauses -- verified by actually compiling, not guessed.
  • Format through YADF, now with real safety rails (chapter 12).

8. AI and tooling integration

Why this matters commercially. An AI assistant reading a large Delphi unit spends enormous effort doing it. Asking drag-lint the same question instead was measured at 269× cheaper on a real file -- roughly 1,300 units of work against 338,500. Across a working day that is the difference between an assistant that is affordable and one that is not.

  • A context bundle: exactly the code needed to answer one question, and nothing else.
  • Machine-readable output from every command.
  • A guarded read-only SQL interface over the database.
  • Exports to Obsidian and to graph formats.

9. Editor and IDE integration

  • RAD Studio plugin: structure view, findings panel, go-to-definition, find usages, hover, completion, a call-graph viewer.
  • A language server, so other editors get the same answers.
  • Quick fixes offered at the cursor.

10. Reporting, maintenance and integrity

  • Reports on uses clauses, dependencies and TODOs.
  • Detects drift between the index and the code.
  • Recovers work from editor buffers after a crash.
  • A project wiki authored in the code itself -- 21 topics were seeded for Micronite from its own units.

11. Component Converter

Converts legacy visual components to modern equivalents -- the Orpheus to DevExpress migration this was built for.

  • A rule book describes the conversion; a validator checks it before anything runs.
  • Converts the code declaration, the form file, the property values and the uses clause together, or refuses the instance entirely -- never half of it.
  • Always previewable before it writes.
  • A visual rule-authoring editor.

Known limitation in this release. When a conversion needs to convert a value as well as a property -- an image being handed to a different image type, for instance -- the image data is currently dropped while the run reports success. Fixing this is the first piece of work after this release (chapter 13). Until then, treat image-carrying conversions as manual.

12. What is new in 1.13.0-alpha

Hovering an interface now tells you what implements it

Point at ImcSTATIONS and the answer is TmcSTATIONS. Implementing classes and derived interfaces are listed separately, because one is something you can create and the other is not. The same fact is written into the generated documentation, so it can be read without any tool.

Formatting is no longer able to damage a file

The format command rewrites source in place. It now: refuses a formatter version old enough to be known-bad; re-reads the file afterwards and checks that the formatter changed only the layout, not what the unit declares -- restoring the original if it did; and offers a preview that writes nothing.

Previously the preview option was accepted and then ignored, so a file could be rewritten by the very command intended to avoid touching it.

Read-only commands are genuinely read-only

Fourteen further commands that only answer questions were quietly upgrading the database they were pointed at. They now refuse a stale database and leave it untouched. This completes a change begun in the previous release.

Two messages that were confidently wrong

  • The converter reported that a form file was missing a component block when the real cause was that the unit had not been indexed. The message cost the conversion team a day. It now names the real condition.
  • The outline command reported that no database covered a file, for files another command listed three databases for. Both now resolve the same way.

13. What is planned

This is a pipeline, not a commitment. Items are listed in the order currently intended, with rough effort. Order and scope change as priorities do.

NextWhat it isRough effort
Image and value conversion Finish the converter so a conversion that must transform a value -- an image handed to a different image type -- carries it across instead of dropping it. Blocks live conversion work today. 3-5 days
Inherited fields in analysis Object analysis currently stops at a class's own fields and misses everything inherited from a shared base. Decided; needs one piece of groundwork first (recognising a generic base class), which by itself improves several other answers. 2-3 days + groundwork
Exception handling Document which exceptions a routine handles, not only which it raises. 2-3 days
Nested routine analysis Variables declared inside nested routines are not currently recorded, which weakens several checks. Requires a full re-read of every index (about five hours, unattended). 2-3 days + re-index
Property references The index records which routines call each other, but not which read or write a property. Closing this improves dead-code detection, purity analysis and impact reports at once. The largest item on the list. weeks

Further out

  • A visual code map. A standalone viewer already exists and already talks to the IDE; the work is to give it professional layout and export. Re-estimated from months to about two to three weeks once it was established that the layout engine should be delegated rather than written. Likely to run on its own track so it does not hold up the engine.
  • Following a call across process boundaries -- tracing a request from a client through to the server routine that serves it. Proven to work end to end; roughly one to two days to finish.
  • Numbers as searchable facts -- port numbers and similar constants are not currently findable by value.
  • More wiki topics from the existing Micronite documentation -- one to two hours.

How quality is held

Every change in this release shipped with a test written before the fix, which was required to fail first. Each also ships what the team calls a positive control -- a second test proving the first one is capable of failing at all. This exists because a test that silently stops checking anything is indistinguishable from a test that passes.

The full test battery is 543 runs, and the release was cut only with all of them green.
