# v0.66 feature plan (scope + prioritization)

> **Status:** ROADMAP-LEVEL plan, drafted autonomously 2026-06-29 after shipping v0.65.0-alpha.
> Decisions below are proposals for the user to review/re-order. Each feature gets its own
> `writing-plans` detailed plan when work on it begins. Baseline: origin/main @ v0.65.0-alpha
> (harness 78/78 + projectchecks 21/21); Stream B (R2 queue + dock status bar) is implemented on
> branch `feature/r2-dock-statusbar`, awaiting the user's manual IDE test + merge.

**Theme:** *finish what v0.65 deferred + the highest-leverage indexer quick win, then design the
big M1 type resolver so v0.67 can execute it.* Keep every CLI change harness-testable; keep IDE
changes behind a manual-test gate.

## Tier 1 -- project-membership accuracy (finish FP-9; the 837 noise)  [v0.66.0]
The v0.65 fixes removed the *bugs* (dotted names, comment hints, `_SERVER`) but the bulk
`unit-not-in-project` volume remains: third-party `dx*`/`cx*`/EurekaLog units and generated
`COMMON\OBJECTS\` units flagged because they are not in the platform library DB and not on disk
*beside* the `.dproj`. This is a search-path-resolution feature, not a quick fix.
- **Read the project's real search paths** from the `.dproj` (`DCC_UnitSearchPath`, `DCC_Namespace`)
  and the IDE library/browsing path; treat a unit resolvable on any of them as "in the build by
  design" -> do not flag.
- **Classify** the remaining used-but-unresolved units: `library` (installed package / browsing
  path), `generated` (under a known shared dir e.g. `COMMON\OBJECTS\`), `server` (`*_SERVER`,
  already suppressed), `project` (hand-written, compiles via search path but never registered).
  Only the last class is actionable -> the rule collapses to the "tiny handful".
- **Testable** via a project fixture (`.dproj` with a search path + a units tree) + the existing
  `lint --project` path; extend `tests/projectchecks` or add a `tests/lint` project fixture.
- Effort: **medium**. Risk: low (more suppression = fewer FPs, aligned with the FP policy).

## Tier 2 -- grep-elimination indexer P1: working-tree / live query  [v0.66.0]
From `docs/superpowers/specs/2026-06-29-grep-elimination-indexer-wishlist.md`, the **highest-leverage**
item: a query mode that re-parses *dirty* (modified-since-index) files on the fly so `query` /
`query --text` reflect the working tree, not the last full index. This removes the main reason we
still fall back to Grep mid-edit (index staleness). 
- Scope: detect files whose mtime > index time (or an explicit `--working-tree` / `--dirty <dir>`),
  parse them in-memory, and overlay their symbols/refs on the DB result set for the query.
- Effort: **medium-large**. Defer the other wishlist items (regex `--text`, indexing non-Delphi
  files into FTS) to v0.66.1 unless cheap.

## Tier 3 -- M1 type & hierarchy resolver (DESIGN in v0.66, EXECUTE in v0.67)
The roadmap's big infrastructure item (`2026-06-28-lint-completeness-roadmap-design.md`): cross-unit
resolution of a symbol's declared type + class/interface hierarchy, resolved through the `uses`
graph. It is the gate for the accurate rule waves and for replacing today's heuristics:
- makes `string-equality-comparison` truly type-aware (drop the v0.64.1 literal-operand heuristic),
- extends `virtual-method-in-constructor` across ancestry (today: same-unit/same-class only),
- unblocks use-after-free-across-calls, interface/abstract rules, and the naming waves.
- **v0.66 action: brainstorm + write the design spec** (storage: resolved type/ancestor columns or
  a resolve pass over the existing `symbols`/`unit_uses` tables? incremental vs full?). Execute in
  v0.67. Big; design-first de-risks it.

## Tier 4 -- rule waves (after M1, likely v0.67+)
- **Wave A** -- additional no-resolver AST/index rules (more built-ins that need only the AST + the
  symbol/refs graph).
- **Wave B** -- naming / convention rules, on by default (roadmap decision). *Per the 2026-06-29
  coverage analysis this is the single cheapest big breadth win (naming is ~0% today, ~14
  deterministic near-zero-FP `.scm` rules); consider pulling it earlier than M1.*
- **NEW long pole (data-flow / CFG engine)** -- the coverage analysis named this the real gap to
  commercial (PAL) parity: a per-routine control-flow graph + def-use pass unlocking
  used-before-assignment, function-result-not-set, set-never-referenced, overwrite-before-read.
  Multi-month engine work, not rule-writing; schedule as its own milestone (M2) after M1.

## Tier 5 -- rule selection / profiles UI (USER REQUEST, target v0.67-0.68)
Let users **enable/disable whole rule groups and individual rules** to check or skip.
- **Rule taxonomy first:** tag every rule with a category (security / naming / resource / exceptions /
  complexity / portability / architecture / style / ...) so groups exist to toggle. (The coverage
  analysis already bins them.)
- **Config:** a profile file (e.g. `drag-lint-rules.json`: per-group + per-rule on/off, severity
  overrides). CLI already has `--disable id,...`; add `--enable`, `--only <group>`, `--profile <file>`,
  and group-level toggles. Default profile = current behavior.
- **IDE UI:** a settings page (checkbox tree: groups -> rules) writing that profile; lint-all / live
  lint honor it. Pairs naturally with the new clickable Messages (triage -> mute a noisy rule/group).
- Effort: medium (taxonomy + config plumbing + a VCL checkbox-tree dialog). Build the CLI profile
  first (harness-testable), then the IDE UI.
