# Design: offering DelphiLSP-backed intelligence behind drag-lint's own protocol

**Status:** DESIGN ONLY -- not implemented, no code written, no engine change made.
**Date:** 2026-08-05
**Author:** converter-editor workstream (planning pass; IDE was in use, so nothing was built)
**Audience:** drag-lint engine team

## 1. Problem

drag-lint answers code-intelligence questions from its own AST index. That index is
broad, fast, cross-project, and -- importantly -- works on code that does not
compile and on files with no project context at all.

What it is not is *compiler-exact*. Generic instantiation, inline-var type
inference, `with`-block member binding and overload selection are all places where
an index approximates what only the compiler truly knows.

Embarcadero ships `DelphiLSP.exe`, which is exactly that missing half: the real
compiler front-end behind an LSP. It runs standalone -- no RAD Studio process
required -- driven by a `.delphilsp.json` config plus the compiler DLL
(`dcc32<ver>.dll`).

**Proposal:** when a Delphi installation is present, drag-lint offers
DelphiLSP-backed answers *behind its own MCP/LSP surface*, alongside index-backed
answers, with provenance attached. When Delphi is absent, behaviour is unchanged.

## 2. Explicit non-goals

* **Not vendoring anyone else's bridge.** A third-party MCP<->DelphiLSP bridge
  exists (`github.com/SkybuckFlying/Delphi-LSP-MCP-Server`, by Skybuck Flying). It
  is a separate project with a license we have not cleared. This design is an
  independent implementation; do not copy from it.
* **Not redistributing DelphiLSP.** We invoke the user's licensed install. Nothing
  Embarcadero-owned is shipped.
* **Not replacing the index.** DelphiLSP cannot answer most of what makes
  drag-lint useful -- `get_impact`, `get_slice`, `get_wiring`, lint rules,
  cross-project search, context bundles. This is additive only.
* **Not a hard dependency.** No Delphi, no degradation beyond losing the extra
  resolver.

## 3. Why this is cheaper than it looks

The expensive part of driving DelphiLSP standalone is producing a valid
`.delphilsp.json`: project URI, `dllname`, `dccOptions`, and a fully-resolved unit
search path. Today those files are generated by the IDE.

**We already compute exactly that data.** `TCompileChecker`
(`src/diagnostics/DRagLint.Diagnostics.CompileCheck.pas`) resolves the IDE global
Library Path from the registry per platform, expands macros, dedups and
existence-filters it, and injects it via `DCC_UnitSearchPath` -- because it has to,
to make `dcc64` work outside the IDE. Config generation is a re-render of data the
engine already has, not new research.

A reference artifact exists in-tree for shape comparison:
`src/cli/drag-lint.delphilsp.json`.

## 4. Architecture

Four pieces, in dependency order.

### 4.1 Discovery

Locate, via the registry keys CompileCheck already reads:

* `DelphiLSP.exe` (observed at `<Studio>\37.0\bin64\DelphiLSP.exe`)
* the matching compiler DLL (`dcc32370.dll` for 37.0)

Result is a capability record: present/absent, version, paths. Absent is a normal,
silent outcome -- not a warning.

### 4.2 Config synthesis

Given a `.dproj` (or a bare `.pas` plus a chosen platform), emit a
`.delphilsp.json` into a cache directory. Reuse CompileCheck's path resolution;
factor the shared part into a unit both call rather than duplicating it.

Regeneration trigger: `.dproj` mtime/hash change, or platform switch.

### 4.3 LSP client

A stdio JSON-RPC client owning a DelphiLSP child process per (project, platform):
`initialize` handshake, document sync (`didOpen`/`didChange`/`didSave`), request
routing, shutdown, and crash restart with backoff.

This is the only genuinely new component.

### 4.4 Resolver merge policy

The real design decision. For the four overlapping request kinds -- hover,
definition, references, completion -- decide who answers.

**Proposed default:** index answers first, because it is always available and
fast. DelphiLSP is consulted when it is available **and** one of:

* the index returned nothing;
* the index returned an ambiguous set (the `TEdit`-resolves-to-FMX class of
  problem, still open as finding 2.5);
* the caller explicitly asked for compiler-exact resolution.

**Provenance is mandatory.** Every row carries its resolver:

```json
"resolved_by": "index" | "delphilsp"
```

This follows the precedent set by `match_kind` in the 2026-08-02 engine work: a
consumer handed a differently-sourced answer in an identical shape, with nothing
marking it, will be misled. Do not repeat that.

## 5. Surface changes

Prefer **not** adding parallel tools (`find_symbol_exact`, ...). Instead:

* an optional `resolver` argument on the overlapping MCP tools:
  `"auto"` (default, per 4.4) | `"index"` | `"delphilsp"`;
* the `resolved_by` field on every returned row;
* on the LSP side, DelphiLSP diagnostics merge into `publishDiagnostics`
  alongside lint findings and `dcc` compiler findings -- the merge point and the
  `compiler_findings` store already exist.

## 6. Risks and open questions

| # | Risk | Note |
|---|---|---|
| R1 | DelphiLSP startup cost and RSS, one process per project/platform | Needs measurement before defaulting `auto` to consult it. Lazy-start on first miss. |
| R2 | DelphiLSP needs a *compilable* project | Legacy units that do not compile get no answer. Index must stay the floor, never a fallback-of-last-resort. |
| R3 | Config drift | Stale `.delphilsp.json` yields confidently wrong answers -- worse than none. Hash-gate regeneration. |
| R4 | Community Edition | Forbids command-line compilation; discovery must treat CE as absent. |
| R5 | Version coupling | `dllname` is version-specific (`dcc32370.dll`). Multi-version installs need the record from 4.1 to pick. |
| R6 | Protocol drift | DelphiLSP's LSP conformance is not documented by Embarcadero; capability negotiation may be partial. |

**Open questions for the engine team:**

1. Is `auto` the right default, or should DelphiLSP be strictly opt-in until R1 is
   measured?
2. Does this interact with finding 2.5 (bare `TEdit` resolving FMX-first)? A
   compiler-exact resolver arguably *is* the `--prefer-namespace` answer you
   proposed -- worth deciding together rather than shipping both.
3. Should `run_compile_check` and DelphiLSP diagnostics de-duplicate, given both
   ultimately come from `dcc`?

## 7. Acceptance criteria (for whoever implements)

1. No Delphi installed -> every existing command behaves byte-identically to today.
2. Delphi installed -> `resolved_by` present on every row of the overlapping tools,
   in both modes.
3. A generated `.delphilsp.json` drives a standalone DelphiLSP to answer
   `textDocument/definition` on a real project **with RAD Studio not running**.
4. A deliberately non-compiling unit still returns index answers, with no hang and
   no error surfaced to the caller.
5. DelphiLSP crash -> automatic restart, and index answers throughout.
6. Measured startup and steady-state cost recorded in the plan, so R1 stops being
   a guess.

## 8. Effort shape (not a promise)

Discovery + config synthesis is mostly re-rendering existing data. The LSP client
is the real work. Merge policy is small in code and large in argument -- settle
section 4.4 and question 1 before anyone writes the client.
