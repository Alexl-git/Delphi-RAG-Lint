## Why this one is worth fixing above its apparent size

`C:\Projects\CLAUDE.md` instructs every session to run
`context --task "modify <QualifiedName>"` *before* reading a large `.pas` file,
on the measured grounds that it is ~60x leaner (~556 vs ~33,762 tokens on ORM3).
When the name is bare the command **succeeds silently and returns nothing**, so
the caller sees no error, concludes there is no context to be had, and falls back
to reading whole files. The failure mode is invisible and it costs exactly the
tokens the feature exists to save. A wrong answer that looks like a legitimate
"nothing here" is worse than a crash.

The bare-vs-qualified split also matters because it is not obvious from the
docs: `query --name` explicitly accepts a qualified name and falls back to
`--qname` on a dotted value, so a reader reasonably expects `--task` to be as
forgiving in the other direction.

## Suggested shape

Resolve the task's symbol through the same path `query --name` already uses
(case-insensitive, bare-or-qualified), and when it yields 0 or >1 candidates say
so on stderr and exit non-zero rather than emitting an empty bundle. If
ambiguity is expected to be common, listing the candidates' qualified names is
the actionable output -- the caller can then re-run with one.

## Guard

A fixture with one uniquely-named routine, asserting that the bare-name and
qualified-name forms produce the SAME non-empty bundle; plus a deliberately
ambiguous name asserting a non-zero exit with the candidates named. The second
half is the positive control -- without it, "always resolve bare names" could be
implemented by silently picking the first match, which is the other way to be
wrong here.
